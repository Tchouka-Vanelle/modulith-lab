Étape 2 — Comprendre l'organisation de Kubernetes
Avant de taper la moindre commande, retenez ces trois rôles :
•​ Le control plane (le cerveau) : kube-apiserver, la seule porte d'entrée du cluster ; etcd, la base de
données qui stocke son état ; kube-scheduler, qui choisit le nœud où placer chaque pod ;
kube-controller-manager, qui fait tourner les boucles de réconciliation.
•​ Les nœuds (les muscles) : sur chacun, kubelet lance les conteneurs, kube-proxy gère le réseau des
Services, et un runtime (ici containerd) exécute les conteneurs.
•​ kubectl (le client) : il ne fait rien lui-même, il envoie des requêtes à l'API server.
À retenir : vous ne lancez pas de conteneurs à la main. Vous décrivez l'état voulu (« je veux 3 copies »),
l'API server l'enregistre, et des contrôleurs font converger en boucle l'état réel vers cet état voulu. Un
pod supprimé est recréé.

Étape 2 — Construire l'image sans Dockerfile
Spring Boot sait construire une image avec les buildpacks : pas de Dockerfile à écrire. L'image obtenue est
découpée en couches (les reconstructions sont rapides), sa base est tenue à jour, elle s'exécute sans les
droits root, et la mémoire de Java y est calculée automatiquement.
1.​ Dans pom.xml, repérez le plugin spring-boot-maven-plugin et ajoutez-lui ce bloc <configuration> :
<configuration>
<image>
<name>demo-modulith-sb4:0.0.1</name>
<env>
<BP_JVM_VERSION>21</BP_JVM_VERSION>
</env>
</image>
</configuration>

L'image porte un numéro de version (0.0.1) et jamais latest : c'est indispensable pour la charger dans le
cluster (étape 3).

COPY ${JAR_FILE} application.jar

COPY --from=builder /builder/extracted/spring-boot-loader/ ./

Étape 3 — Exposer le Modulith par un Service

À retenir
•​ Kubernetes est déclaratif : vous décrivez l'état voulu, il le maintient.
•​ Un Service sélectionne ses pods par label ; l'IP d'un pod ne sert jamais directement.
•​ Disponibilité (readiness) = trafic, vie (liveness) = redémarrage ; jamais de dépendance externe sur
la sonde de vie.
•​ Une application multipliée doit être sans état ; ses données vont dans une base partagée.
•​ Un Secret est encodé en base64, pas chiffré.
•​ Après chaque modification : construire l'image, kind load docker-image, kubectl rollout
restart.

Questions de réflexion
•​ Pourquoi un Service ne connaît-il pas ses pods à l'avance ? Que se passe-t-il quand un pod est
recréé ailleurs ?
•​ Pourquoi le tunnel port-forward ne permet-il pas de voir la répartition entre les pods ?
•​ Que se passerait-il si la sonde de vie vérifiait l'accès à Postgres ?
•​ Les 3 pods partagent maintenant la même base. Est-ce suffisant pour découper l'application en
plusieurs services ? Que faudra-t-il changer ?
